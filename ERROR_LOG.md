### 1. Typing selector caused endless re-renders

- **Symptom:** components that read the typing indicator could re-render forever.
- **Cause:** the selector `s.typing[id] ?? []` returned a **new** empty array on every call. Zustand compares selector results by reference, so it saw a change on every render.
- **Fix:** return one shared constant (`NO_IDS`) when nobody is typing, so the reference stays the same.
- **Files:** `frontend/src/store/chat.ts`, `chat/MessageList.tsx`, `chat/ChatPane.tsx`

### 2. Messages arriving in an open chat were never marked read

- **Symptom:** if the recipient already had the chat open, the sender's message stayed at "delivered" and never turned "read".
- **Cause:** "mark as read" was triggered by `unread_count > 0`. A message arriving in the chat you're looking at doesn't increase the unread count, so the read request was never sent.
- **Fix:** compare the last message id with **my own read watermark** (`last_read_id`) instead. If the newest message is from someone else and is past my watermark, mark it read. The server's receipt event then moves my watermark, so the request isn't sent twice.
- **Files:** `frontend/src/components/chat/ChatPane.tsx`

### 3. Lint errors: `setState` called inside effects

- **Symptom:** `react-hooks/set-state-in-effect` errors in the composer and the settings panel.
- **Cause:** the composer cleared its text in an effect whenever the chat changed, and the settings panel loaded the saved theme in an effect. Both cause an extra render pass.
- **Fix:** the chat pane is rendered with `key={conversation.id}`, so switching chats remounts the composer with empty state and the reset effect isn't needed. The theme is read with a lazy initializer: `useState(loadTheme)`.
- **Files:** `frontend/src/components/chat/Composer.tsx`, `SettingsPanel.tsx`, `Messenger.tsx`

### 4. Could not test two users locally on two origins

- **Symptom:** opening the app at `127.0.0.1:3000` (to get a second login next to `localhost:3000`) showed a blank page.
- **Cause:** the Next.js dev server only serves its dev assets to its own origin, so the second origin never loaded the app. Both users also can't share one origin, because the token lives in that origin's `localStorage`.
- **Fix:** for local tests, the second user was played by a small Python script that logs in over REST and listens on the WebSocket. For the deployed app, use one normal window and one private window.

### 5. `.env.example` was silently left out of git

- **Symptom:** `frontend/.env.example` existed on disk but was missing from the commit.
- **Cause:** the `.gitignore` generated by `create-next-app` inside `frontend/` contains `.env*`, which also matches `.env.example`. The root `.gitignore`'s exception `!.env.example` didn't apply to that nested file.
- **Fix:** deleted the nested `.gitignore` and kept a single root `.gitignore` covering both apps. Verified with `git check-ignore -v`.
- **Files:** `.gitignore`

### 6. Browser tab showed the Next.js "N" logo

- **Symptom:** the browser tab icon, and a badge in the page corner, showed an "N".
- **Cause:** the default `favicon.ico` from the scaffold, plus the Next.js dev-mode indicator.
- **Fix:** replaced the favicon with an SVG of the Signal mark (`app/icon.svg`, which Next.js serves automatically) and set `devIndicators: false`. The same mark is used on the login and welcome screens through one `SignalLogo` component.
- **Files:** `frontend/src/app/icon.svg`, `components/ui/SignalLogo.tsx`, `next.config.ts`

### 7. A slow server start logged users out

- **Symptom (found in review):** reloading the page while the backend was starting up would have logged the user out.
- **Cause:** the session-restore code deleted the saved token on **any** error, including timeouts and 5xx errors while Render wakes the server.
- **Fix:** only an explicit `401 Unauthorized` ends a session. Network or server errors keep the token.
- **Files:** `frontend/src/store/chat.ts`

### 8. Render could not see the new repository

- **Symptom:** Render's "New Web Service" list showed only an older repository.
- **Cause:** Render's GitHub app had been granted access to selected repositories only.
- **Fix:** Credentials → **Configure in GitHub** → kept "Only select repositories" and added `Signal-Clone`. Access to the existing project stayed as it was.

### 9. API root URL returned `{"detail":"Not Found"}`

- **Symptom:** opening the Render URL showed a JSON 404, which looks broken to a reviewer.
- **Cause:** the API has no route at `/`; everything lives under `/auth`, `/conversations`, `/docs`, and so on.
- **Fix:** `GET /` redirects to the interactive API docs at `/docs`.
- **Files:** `backend/app/main.py`

### 10. Messages stopped going through between two users after a redeploy

- **Symptom:** Alice and Bob, in two windows, couldn't see each other's new messages. Each saw the other as "last seen", and the seeded messages showed different timestamps in each window.
- **Cause:** a `git push` triggered a Render redeploy. The free tier's disk is wiped on every deploy, so the new server started with a fresh SQLite database and no sessions. Alice's window had loaded before the deploy and kept working with the old server and an old token; Bob logged in on the new one. The client didn't notice its token had become invalid:
  - REST calls failed, but the UI kept showing old data.
  - The WebSocket was rejected *before* the handshake, which the browser reports as a generic close code `1006`, so the client just kept retrying.
- **Fix:**
  - Server: accept the socket, then close it with code **4401**, so the browser sees *why* it was closed.
  - Client: a `401` from any API call or a `4401` socket close ends the session and shows "Your session expired. Please log in again."
  - Client: when the socket reconnects after a drop, it reloads conversations and clears cached message lists, so events missed while offline aren't lost.
- **Verified:** with a logged-in tab open, the local backend was restarted with a wiped database. The tab returned to the login screen within seconds, and after logging in again both users saw each other's messages in real time.
- **Files:** `backend/app/routers/ws.py`, `frontend/src/lib/api.ts`, `lib/socket.ts`, `store/chat.ts`, `hooks/useRealtime.ts`

### 11. Data resets on Render's free tier

- **Symptom:** after a redeploy, or after the service sleeps (15 minutes without traffic), all data returns to the seed state and users must log in again.
- **Cause:** Render's free web services have an ephemeral filesystem, and the SQLite file lives on it.
- **Decision:** kept as a documented limitation (see the README's assumptions). The brief requires SQLite, the seed rebuilds a usable demo automatically, and fix #10 handles resets cleanly.
- **Options considered:**
  - **Hosted SQLite (Turso / libSQL):** keeps SQLite and survives restarts, but adds an external service and credentials.
  - **Render persistent disk:** paid plans only.
  - **A keep-alive pinger to stop the sleep:** rejected. Free instance hours (750/month) are shared by every free service in the account, and staying awake 24/7 (~744 hours) would starve other services.
